# SSD 및 BMO 실행 구조 후속 점검

> [Issue #1](https://github.com/GUNOBAE/BGH_BMO_NEXUS/issues/1)의 읽기 전용 점검 안내다. PR #2 작성 이후 **소유자가 기존 도구의 Pi 실행과 모의 테스트 31개 통과를 보고**했다([현장 기록의 후속 결과](09_PI_BASELINE_KR.md#후속-점검-결과-2026-10-25)). 이는 SSD 정상 판정이 아니다. SSD 데이터와 BMO 종료 방식은 미확인이고, [Phase 2A의 추가 진단 절차](12_NVME_TRIAGE_KR.md)는 아직 Pi에서 실행하지 않았다.

## 실행 방법과 범위

소유자가 읽기 전용 현장 점검을 승인한 뒤, Pi의 NEXUS 저장소 루트에서 실행한다.

```bash
bash scripts/inspect_pi_followup.sh
```

Bash와 Python 3 표준 라이브러리를 사용한다. `sudo`가 필요하지 않으며, 없는 도구를 설치하지 않는다. 결과는 터미널의 표준 출력(stdout)에만 표시하고 보고서·스냅샷·로그 파일을 만들지 않는다. 파일로 저장하는 `>`나 `tee`도 사용하지 않는다. 기존 `inspect_pi.sh`보다 출력 항목을 줄인 별도의 후속 도구이므로, 기존 점검 원문을 공개해도 된다는 뜻은 아니다.

이 도구는 저장장치와 현재 실행 구조를 관찰한다. BMO 앱, systemd 설정, 자동실행 파일, 네트워크 설정은 변경하지 않는다. 프로세스를 종료하거나 재시작하지 않고, SSD에 파일을 쓰거나 새 마운트를 만들지 않는다. 복구해야 할 호스트 설정 변경은 없다. 코드 변경을 되돌리려면 이 PR의 추가 파일을 사용하는 일을 중단하고, 저장소 변경은 별도 리뷰로 되돌린다.

## 무엇을 조회하는가

아래는 도구 내부의 조회 명령이다. **각 명령을 따로 실행하면 후속 도구의 출력 제한이 적용되지 않는다.** 도구는 원문을 메모리에서 해석한 뒤 필요한 값만 출력하고, 명령의 오류 원문도 그대로 내보내지 않는다.

| 조회 | 하는 일 / 필요한 이유 | 결과를 읽는 방법 |
|---|---|---|
| `lsblk --bytes --json --output NAME,TYPE,SIZE,FSTYPE` | 블록 장치와 파티션의 보고 크기를 바이트 단위로 읽는다. JSON은 프로그램이 필드를 구별하기 위한 형식이다. | NVMe 장치 전체와 하위 파티션 크기를 비교한다. 장치가 0B인데 파티션만 큰 값이면 인식 불일치가 남아 있다. |
| `/sys/class/block/nvme…/size` 읽기 | 커널이 보고하는 NVMe 섹터 수를 확인한다. 숫자로 확인된 장치 이름에 대응하는 `size`만 읽는다. | 이 값은 512바이트 단위의 섹터 수다. `lsblk`의 바이트 수와 함께 비교하며, 0이나 읽기 실패는 정상 확인으로 취급하지 않는다. |
| `findmnt --json --mountpoint / --output SOURCE,FSTYPE` | 현재 프로세스가 보는 루트(`/`) 파일시스템의 장치와 종류를 조회한다. | 알려진 일반 장치명만 표시한다. 별칭·사용자 정의 경로는 비공개로 처리한다. 기존 SD 부팅 기록과 비교할 단서이며 SSD 상태 판정은 아니다. |
| `findmnt --json --list --output SOURCE,FSTYPE` | 현재 프로세스가 보는 마운트 목록을 조회한다. | NVMe의 `/dev/장치명`과 SOURCE가 정확히 같은 레코드 수만 표시한다. 개인 마운트 경로·네트워크 주소는 출력하지 않는다. |
| `ps -eo comm=` | 짧은 프로세스 이름만 읽어, 알려진 이름별 개수를 센다. PID와 부모 PID도 조회하지 않는다. | Python, Node, Chromium 같은 이름만으로 BMO 앱이라고 확정할 수 없다. 실행 인자와 환경변수는 조회하지 않는다. |
| `systemctl list-units --type=service --state=running --no-pager --plain --no-legend` | 현재 실행 중인 시스템 서비스 목록을 조회한다. | 목록에 있다는 것은 실행 중이라는 관찰이다. BMO 런처나 안전한 종료 방법이 확인됐다는 뜻은 아니다. |
| `systemctl list-unit-files --type=service --no-pager --no-legend` | 등록된 시스템 서비스 파일 목록과 설정 상태를 조회한다. | `enabled`는 자동 시작 관련 설정 상태이지 현재 실행 중이라는 뜻이 아니다. `disabled`여도 수동·의존성 등으로 실행될 수 있다. 서비스 본문이나 `Environment=`, `ExecStart=`를 출력하지 않는다. |
| 위 두 `systemctl` 명령에 `--user` 추가 | 명령을 실행한 사용자의 systemd 서비스 목록을 조회한다. | 다른 사용자의 서비스와 GUI 세션 전체를 조사하는 것은 아니다. 사용자 버스에 연결할 수 없으면 해당 항목은 미확인이다. |

기본 출력은 고정된 일반 프로세스 이름과 알려진 서비스 이름으로 제한한다. 이름 자체에 개인 정보가 들어갈 수 있는 사용자 정의 BMO 서비스는 후보 개수만 표시하고 이름은 숨긴다. 따라서 이 결과는 **전체 프로세스·서비스 목록이 아니며**, BMO 실행 계약을 대신하지 않는다. 숨긴 이름과 정확한 런처는 BMO 담당자가 비공개로 확인해야 한다.

마운트 레코드 수는 제한적인 단서다. SOURCE의 별칭(`/dev/disk/by-uuid/…` 등), 암호화·LVM의 mapper 경로, 하위 볼륨 표기를 NVMe에 연결해 추적하지 않는다. **레코드 0개는 마운트 부재의 증명이 아니다.** 양수여도 서비스가 요구하는 경로에 올바른 파일시스템이 마운트됐는지, 필요한 권한이 있는지, 서버를 시작해도 되는지는 확인하지 않는다. 향후 서비스의 실제 마운트 검사를 이 도구로 대체하면 안 된다.

UUID, 디스크 라벨, 일련번호, 개인 경로, IP 주소, 프로세스 명령 인자, 환경변수, 서비스 설명, 커널 로그 원문은 기본 출력에 포함하지 않는다. 조회 도구가 없거나 권한·세션 문제로 실패하면 오류 원문 대신 미확인 상태를 표시하고 가능한 나머지 조회를 계속한다. 각 외부 조회는 8초 안에 끝나지 않으면 미확인으로 처리한다.

종료 코드 `0`은 조회 시도가 끝났다는 뜻이며 미확인 항목이 있어도 반환한다. Python 3 자체가 없을 때도 설치 없이 안내하고 `0`으로 끝난다. 인자를 넘기면 `2`, 예상하지 못한 처리 실패는 오류 원문 대신 고정 안내를 출력하고 `1`로 끝난다. **종료 코드 `0`은 SSD나 BMO의 정상 판정 또는 모드 전환 허가가 아니다.**

## SSD 관찰별 다음 단계

| 관찰 | 판단할 수 있는 범위 | 다음 읽기 전용 확인 |
|---|---|---|
| NVMe 장치를 찾지 못함 | 이번 조회에서 보이지 않음. 물리적으로 없거나 비었다고 확정 불가 | `lsblk` 조회 실패와 성공한 목록에 이름이 없는 경우를 구분하고, 기존 기록과 비교한다. 이때 sysfs를 별도로 탐색하지는 않는다. |
| 장치 크기 0B, 파티션 크기는 큰 값 | 기존 1차 기록과 같은 불일치가 지속될 수 있음 | 커널 보고 섹터 수와 비교한다. 필요할 때만 아래의 커널 메시지를 소유자가 로컬에서 검토한다. |
| 장치와 파티션의 양수 크기가 일관됨 | 그 시점의 용량 보고가 일관됨 | 파일시스템 탐지 여부와 현재 마운트 관찰을 별도로 확인한다. 데이터 무결성이나 장시간 안정성은 별도 검증이다. |
| FSTYPE 미탐지 | 도구가 파일시스템 종류를 확인하지 못함 | 기존 데이터 유무를 미확인으로 남긴다. 빈 SSD 또는 초기화 가능한 SSD로 해석하지 않는다. |
| 동일 SOURCE 마운트 레코드 0개 | 장치명과 SOURCE가 정확히 같은 레코드가 없음. 별칭·mapper·하위 볼륨은 미확인 | 장치 매핑·권한·조회 범위를 비공개로 추가 확인한다. 마운트 부재로 확정하거나 새 마운트를 만들지 않는다. |
| 파일시스템이나 마운트가 관찰됨 | 종류 또는 연결에 관한 단서가 있음 | 기존 데이터의 소유자·용도·백업 상태를 확인한다. 서버가 사용할 수 있다는 승인으로 간주하지 않는다. |

0B가 계속되면 원인과 데이터 상태를 **미확인**으로 유지한다. 출력만으로 전원·PCIe 링크·컨트롤러·커널 중 원인을 특정하지 않는다. 먼저 비공개로 기존 관찰과 오류 종류를 비교하고, 데이터 보존을 우선하는 다음 조사안을 검토한다. 재부팅, 케이블/PCIe 분리, 드라이버 재로딩, 재스캔, 포맷·파티션 변경, 새 마운트, 복구 프로그램의 쓰기 작업은 이번 점검 범위에 없다. 그런 조치가 필요하면 정확한 명령과 복구 경로를 먼저 제시하고 별도 승인을 받는다.

## 선택 사항: 커널 메시지는 소유자가 로컬에서만 검토

기본 도구는 커널 로그를 읽지 않는다. NVMe/PCIe 관련 메시지가 더 필요하다고 판단한 경우에만, 소유자가 Pi의 비공개 터미널에서 다음 읽기 전용 조회를 검토한다.

```bash
journalctl -k -b --no-pager | grep -Ei 'nvme|pcie'
```

`journalctl -k -b`는 이번 부팅의 커널 메시지를 읽고, `grep`은 NVMe/PCIe 문자열이 있는 줄만 고른다. **문자열 필터는 비밀정보 삭제 기능이 아니다.** 결과에 장치 일련번호, 개인 경로, 주소 등이 남을 수 있다. 오류 원문도 공개하지 않는다. 권한이 없으면 미확인으로 남기고, 이 안내를 따라 권한을 올리거나 패키지를 설치하지 않는다.

공유가 필요하면 원문을 복사하는 대신, 소유자가 내용을 읽고 “용량 보고 0B 지속”, “NVMe 관련 오류 관찰 여부”, “상세 원인 미확인”처럼 일반화한 결론만 새로 작성한다. 식별번호·주소·토큰·개인 경로를 제거했는지 확인한 뒤 공유한다. 원본 로그와 스크린샷, 자동 저장한 보고서는 Git이나 공개 Issue/PR에 올리지 않는다.

## BMO 담당 Codex에게 필요한 사실

아래 항목은 아직 받은 계약이 아니다. 로봇 담당자가 기존 코드와 실행 구조를 확인한 뒤, 민감정보를 제외한 답을 전달해야 한다.

- [ ] 정확한 시작 진입점: 실행 파일/래퍼/서비스와 실행 사용자. 경로·실행 인자에 비밀정보가 있으면 비공개로 관리한다.
- [ ] 부팅·로그인 시 자동실행 위치: systemd 시스템/사용자 유닛, GUI autostart, 로그인 스크립트, 수동 실행 중 실제 사용 방식.
- [ ] 안전한 종료 계약: 지원하는 종료 요청, 정상 종료 완료를 판별하는 기준, 제한 시간과 실패 시 처리. 확인 전에는 종료 시험을 하지 않는다.
- [ ] 자식 프로세스 정리: 얼굴 브라우저, 음성, 카메라, RP2040 연결을 누가 소유하며 종료 후 무엇이 남는지.
- [ ] Ollama 의존 여부: BMO가 언제 사용하는지, 로봇과 서버 어느 쪽의 관리 범위인지. 확인 전에는 변경하지 않는다.
- [ ] SSH·Tailscale·VNC·네트워크와 `bmo-case-fan.service`를 유지하면서 복구할 수 있는 경로.

프로세스 이름별 개수는 이 질문의 단서일 뿐이며, 부모·자식 관계나 종료 시 정리 동작은 이 도구로 확인하지 않는다. 냉각팬 서비스가 발견됐다고 BMO GUI를 관리하는 서비스라고 간주하거나, Python 프로세스를 일괄 종료하지 않는다.

## 오프라인 검증과 실제 Pi 확인을 구분

개발 환경에서는 조회 명령과 sysfs 읽기를 모의 데이터로 대체한다. 테스트 때문에 실제 Pi의 디스크·서비스·프로세스를 조회하거나 변경하지 않는다.

```bash
bash -n scripts/inspect_pi_followup.sh
python3 -B -m unittest discover -s tests -v
```

`bash -n`은 셸 문법만 검사하며 스크립트를 실행하지 않는다. Python 테스트는 0B/미존재 장치, 파일시스템·마운트 요약, 조회 도구 부재, 사용자 systemd 실패, 민감정보 비출력 등 모의 상황에서 동작을 확인한다. `shellcheck`가 설치된 개발 환경에서는 새 셸 스크립트도 검사한다. 없으면 **미실행**으로 기록하고 설치하지 않는다. 실제 실행한 테스트 명령과 결과는 PR에 적는다.

아래는 소유자 승인 후 확인할 현장 기준이다. 기존 도구 실행과 모의 테스트 통과는 위 현장 기록의 소유자 보고를 따르며, 그 보고만으로 아래 각 항목이 모두 검증됐다고 간주하지 않는다.

- [ ] 일반 사용자로 후속 도구를 실행하고 보고서 파일이 만들어지지 않는지 확인.
- [ ] NVMe 장치/파티션 용량과 커널 섹터 수를 대조하고, 파일시스템·마운트 미확인을 구분.
- [ ] 출력에 인자·환경변수·개인 경로·주소·일련번호·원본 로그가 없는지 검토.
- [ ] 사용자 systemd 조회 불가 등의 표시를 정상 상태로 오해하지 않았는지 확인.
- [ ] BMO 동작과 관리 접속·냉각팬의 상태가 유지되는지 소유자가 관찰. 이 도구는 이를 바꾸거나 정상 동작을 자동 보증하지 않는다.

## 공개 보고 양식
