# 보안: 공개 웹 vs 개인 BMO/클라우드

## 공격 표면을 작게 만든다

이 프로젝트는 같은 OS에서 BMO와 웹 서비스가 번갈아 실행된다. **모드 분리 ≠ 보안 격리.** 공개 서버가 호스트 권한을 탈취당하면 로봇 설정·토큰·로컬 데이터도 위험할 수 있다.

| 자원 | 경로 | 공개 정책 |
|---|---|---|
| 테스트용 정적 웹 한 개 | Cloudflare Tunnel → 공개 컨테이너 | 외부 허용(별도 검수 후) |
| 개인 파일 웹 UI | Tailscale 사설망 → 앱 인증 | 공개 금지 |
| 서버 관리/SSH | Tailscale + SSH 키 | 공개 금지 |
| 백업 스냅샷/DB | SSD 비공개 영역 | 공개 금지 |
| BMO 내부 API·카메라·마이크·RP2040 | BMO 워크로드 전용 | 공개 금지 |

## 반드시 지킬 보안 체크리스트

- 공유기 포트포워딩(80/443/22)을 처음부터 열지 않는다. Cloudflare Tunnel은 outbound 연결로 공개 앱을 연결할 수 있지만 **서비스 인증을 자동 보장하지 않는다.**
- 공개 사이트와 개인 파일의 폴더/컨테이너 네트워크/비밀키를 분리한다. `docker.sock`, `/`, `/home`, 장치 디렉터리, `~/.ssh`를 공개 컨테이너에 마운트하지 않는다.
- 컨테이너는 가능하면 비루트 실행, 최소 권한, 읽기 전용 파일시스템, 필요한 곳만 쓰기, 적절한 리소스 제한.
- `docker` 그룹에 속하면 사실상 호스트 관리자급 권한이 될 수 있다. 웹앱 사용자에 Docker 관리 권한을 주지 않는다.
- Docker 포트 공개 설정은 일부 방화벽 도구(UFW 등)의 기대와 다르게 동작할 수 있다. 초기에는 `127.0.0.1` 바인딩과 외부에서의 실제 접속 시험을 기본으로 한다.
- Cloudflare/Tailscale/GitHub 계정은 MFA, 별도 최소권한 토큰, 교체/취소 절차를 마련한다.
- 파일 업로드 공개 서비스는 처음부터 만들지 않는다. 사용자 코드를 실행하는 공개 웹 IDE/터미널은 동일 Pi에 두지 않는다.
- 비밀키/도메인 토큰은 Git 저장소와 웹 빌드 폴더 밖의 권한 제한된 설정에 둔다.
- 앱 업데이트 전 백업, 적용 후 비공개→공개 검사를 반복한다.

## 단계별 외부 접속 검증

1. localhost만: Pi 외부에서 아무것도 열리지 않는지 확인.
2. Tailscale만: 승인된 개인 기기에서만 파일 UI/관리 SSH 접속.
3. Cloudflare 공개: 사전 등록한 **정적 테스트 사이트 주소 한 개**만 모바일 데이터로 접속.
4. 외부 모바일 데이터에서 개인 파일 UI/관리 기능 접속 실패 확인.
5. SERVER → ROBOT 전환: 공개 데모가 연결 중지/오프라인 처리되는지 확인.
6. 비정상 정지 및 Pi 재부팅: 의도하지 않은 자동 공개가 발생하지 않는지 확인.

## 운영 현실

- BMO 모드에서는 Pi에서 직접 제공하는 동적 테스트 웹사이트가 오프라인일 수 있다.
- 정말 항상 열려 있어야 하는 포트폴리오는 GitHub Pages 등 별도 정적 호스팅으로 분리한다.
- 인터넷에 공개할 필요 없는 파일 저장·백업은 **사설 접근만 허용**하는 것이 원칙이다.
- 외부 사용자가 업로드하거나 임의 코드를 실행하는 테스트 서버는 가정용 Pi의 개인 파일과 함께 호스팅하지 않는 방향을 우선 검토한다.
