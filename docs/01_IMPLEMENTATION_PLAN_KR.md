# BMO NEXUS — 구현 순서와 검수 기준

> 절대 원칙: 기존 BMO를 훼손하지 않는다. **읽기 전용 점검 → 원본 보호 → 사설 운영 → 모드 전환 → 검증 후 제한적 공개**. 순서는 OS/저장장치/서비스 실측 결과에 따라 조정 가능하다.

## 단계 0 — GitHub 저장소 및 프로젝트 경계 정리

- 새 저장소 `GUNOBAE/BGH_BMO_NEXUS`를 만든다. BMO 로봇 원본 `BGH_BMO`는 계속 별도 관리한다.
- 여기는 시스템의 설계·진행 현황·전환·배포·백업 스크립트만 보관한다.
- UI/포트폴리오/웹사이트 제작은 다른 채팅/별도 폴더에서 한다.
- GitHub에는 `.env`, SSH 비밀키, Tailscale/Cloudflare 토큰, 개인 파일, 실제 백업 데이터 등을 올리지 않는다.

**완료 조건:** 공개 README에 프로젝트가 기획 단계임이 적혀 있고, 원본 BMO 파일이 변경되지 않았다.

## 단계 1 — Pi의 현재 상태 진단 (가장 먼저)

```bash
cd ~/BGH_BMO_NEXUS      # 실제 내려받은 디렉터리에 맞게 조정
bash scripts/inspect_pi.sh
```

수동 확인 명령(전부 읽기 전용):

```bash
cat /etc/os-release                         # OS 및 배포판 버전
uname -m                                    # arm64(aarch64) 여부
lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINTS # SD/SSD와 마운트 지점
findmnt -no SOURCE,FSTYPE,TARGET /          # 현재 OS 루트가 어떤 장치에 있는지
df -hT                                      # 디스크 사용량
free -h                                     # 메모리
systemctl list-units --type=service --state=running --no-pager
systemctl list-unit-files --type=service --no-pager
ss -lnt                                     # TCP LISTEN 포트, 외부 공개 여부는 뜻하지 않음
```

확인할 질문:

1. OS가 Raspberry Pi OS 64-bit인가? Debian 기반인가? 현재 BMO GUI를 어떻게 자동 시작시키는가?
2. `nvme0n1`이 보이는가? OS `/`가 SD인지 SSD인지? SSD에 중요한 데이터가 있는가?
3. 얼굴/대화/Fish Audio/RP2040/카메라/화면 앱의 시작·중지 방식은 무엇인가? `systemd`, 로그인 autostart, 수동 CLI 중 무엇인가?
4. `tailscaled`, `docker`, `cloudflared`, `nginx`, `apache`, `caddy` 등이 이미 있는가? 충돌할 포트는 무엇인가?
5. 전원/냉각/UPS/저장장치가 장시간 서버 운영에 안정적인가?

**완료 조건:** 자동 시작 진입점, 부팅 디스크, SSD 데이터 경로, 공개 포트, 실행 사용자 및 권한을 메모했다.

**금지:** `mkfs`, `fdisk` 쓰기, `dd`, `rpi-imager`, `/boot` 수정, `sudo apt upgrade`, 포트포워딩, 기존 BMO `systemctl disable` 등은 이 단계에서 하지 않는다.

## 단계 2 — 현재 BMO 원본 보호 및 복구 시나리오

- 기존 `BGH_BMO` 코드 **Git 커밋된 것뿐 아니라 미커밋/미추적 파일**을 포함해 별도 장소에 복사한다. API 비밀키는 암호화된 별도 보관으로 취급한다.
- 화면 R10 최종 승인 산출물, 음성 파일/설정, RP2040 펌웨어, 현재 시작 명령을 기록한다. R10 화면은 승인 기준이지만 Pi 전체 통합 성공 여부와 혼동하지 않는다.
- 백업 저장 위치를 실제로 확인한다. SD와 SSD가 같은 Pi에 있으면 동시에 파손될 수 있다. **외장 저장장치 또는 다른 기기**에도 복사한다.
- 백업이 존재하는 것만 확인하지 말고, **일부 파일을 별도 폴더에 복원해 열어본다.**

**완료 조건:** BMO 원본과 설정을 정상 재현할 수 있는 복구 경로가 있다.

## 단계 3 — 서버용 데이터 영역 분리

- 확인된 SSD의 **기존 데이터가 손실되지 않도록**, 현재 마운트 정책을 확인한 뒤 `vault/`, `mirrors/`, `appdata/`, `sites/` 등의 디렉터리를 만든다.
- SSD의 고정 마운트 지점은 `findmnt`, `blkid`, `lsblk -f`로 확인한 뒤 UUID 기준으로 설계한다. 임의 장치명에 의존하지 않는다.
- SSD가 마운트되지 않으면 **서버 앱 시작을 중단**하도록 설계한다. 경로가 비었을 때 SD로 대량 기록하는 사고를 막는다.
- `df -hT`와 `du -sh`로 여유 공간을 확인하고, 파일 서비스마다 저장 할당량/최대 파일 크기를 설정한다.

**완료 조건:** 원본 BMO와 서버 파일이 저장 위치·권한 측면에서 구별되며, SSD 연결 실패를 감지한다.

## 단계 4 — 서버 도구의 사설망 시험

- OS/아키텍처 확인 후 Docker Engine + Compose 플러그인 설치를 검토한다. Raspberry Pi OS 64-bit는 Docker의 Debian/arm64 경로를 기준으로 확인한다.
- **우선 공개 기능 없이** 테스트용 컨테이너 1개를 localhost에서 실행·정지해 Compose 원리를 배운다.
- `restart: "no"`로 서버 컨테이너가 BMO 모드에서 저절로 살아나지 않게 한다. 기존 Docker 서비스가 있다면 정책 확인이 먼저다.
- 파일 클라우드는 SFTPGo의 WebClient부터 검토하되, 사설 접근(Tailscale) + 별도 인증을 두고 디스크 매핑을 제한한다.
- 서버가 종료되어도 개인 파일이 삭제되지 않는지, 다시 켜도 데이터가 남는지 확인한다.

**완료 조건:** 로컬 접속, 파일 업로드/다운로드, 컨테이너 종료/재시작, 권한 검증 완료. 공개 포트는 아직 없다.

## 단계 5 — 모드 전환 제어 구현

- **현재 BMO를 띄우는 정확한 서비스/프로세스**를 확인한 다음 전환 제어기를 구현한다. 새 BMO 시작 명령을 임의로 추측하지 않는다.
- 초기에는 인증된 로컬 CLI 명령만 지원한다: `nexus mode robot|server|maintenance` (계획 명령; 아직 구현 전).
- 전환은 잠금 → 공개 터널 중지 → 현재 모드 종료 → 종료 확인 → 대상 모드 준비 검사 → 대상 시작 → 건강 확인 → SERVER일 때만 공개 허용 순이다.
- 실패 시 신규 서비스 실행 금지, 공개 연결 차단, 오류 메시지 남기기. SSH/Tailscale 관리 접속을 무턱대고 끊지 않는다.
- 시스템 부팅 자동실행 정책은 **기존 BMO 동작을 먼저 조사한 다음** 별도로 확정한다.

**완료 조건:** 양쪽 모드에서 3회 이상 왕복하고, 재부팅/종료 실패/SSD 제거 모의 상황에서 불필요한 공개와 동시 실행이 없음을 검증했다.

## 단계 6 — GitHub 백업과 복원 검증

- 처음에는 Git 저장소(커밋/브랜치/태그)만 mirror하고, restic으로 **날짜별 시점 스냅샷**을 생성한다.
- 개인 저장소는 인증을 별도 관리하고, 백업은 암호화하며, 스냅샷 저장소는 원본 미러 폴더와 구분한다.
- 서버 모드가 아닐 때 백업 작업이 일어나지 않도록 관리한다. 스케줄 시간을 놓치면 서버 모드 복귀 시 조건부로 실행하는 방안을 검토한다.
- GitHub Issue/PR/Release 첨부물/Wiki/설정/Secrets는 Git mirror에 포함되지 않으므로 필요한 것부터 별도 API/CLI 백업 설계.

**완료 조건:** 임의 리포지터리의 특정 시점을 복원하고, 최소 커밋·브랜치·파일 상태를 확인했다.

## 단계 7 — 공개 사이트 1개로 보안 검증

- 공개 웹사이트는 별도 채팅에서 만들고, 여기서는 **승인된 read-only 테스트 사이트 한 개만** 공개한다.
- Cloudflare Tunnel로 선택한 서비스에 연결. 일반적으로 공유기 포트포워딩은 필요하지 않다.
- 클라우드 저장소/SSH/Docker API/모드 변경 UI/백업은 절대 공개 경로에 넣지 않는다.
- 실제 외부망(휴대폰 모바일 데이터)에서 승인된 주소만 열리고 관리 주소는 열리지 않는지 테스트한다.
- BMO 모드 전환 시 외부 공개 연결이 끊기는지 확인한다. 공개 페이지는 BMO 모드 동안 오프라인일 수 있다.

**완료 조건:** 공개 1개 성공 + 비공개 항목의 외부 접근 차단 + BMO 시연 회귀 테스트 완료.

## 단계 8 — 운영과 확장

- CPU 온도, 전력/UPS, RAM, SSD 사용률, 백업 최신 시각, 로그 용량을 점검한다.
- 서비스 업데이트는 버전 고정 → 변경 기록 → 백업 → 업데이트 → 기능 시험 순.
- BMO 로봇 얼굴/음성/버튼/팔의 통합이 변경되면 SERVER → ROBOT 전환 회귀 테스트를 수행한다.
- 서비스가 늘면 실제 RAM 사용량과 전력·발열을 관찰해 상시 실행 범위를 제한한다.

## 하지 않을 것

- BMO 화면/음성 코드를 서버용으로 바꾸지 않는다.
- 웹 대시보드 UI를 이 작업에서 구현하지 않는다.
- 공개 인터넷에서 서드파티 코드 실행이나 사용자 업로드 웹앱을 무작정 허용하지 않는다.
- 실제 SSD/SD 확인 없이 포맷하지 않는다.
